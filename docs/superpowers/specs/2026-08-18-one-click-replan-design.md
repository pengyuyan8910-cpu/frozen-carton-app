# 一键产品池重排设计

## 目标

在不重构现有小程序、不改变上新/淘汰生命周期、不直接覆盖店员端正式方案的前提下，把“新增门店”和“产品池变化”统一接入同一套严格排柜引擎。

最终运营闭环：

`完成上新/淘汰 → 导出当前产品池 → 一键生成排柜草稿 → 人工复核 → 导出最新版底表 → 上传 GitHub → Actions 复核通过后更新小程序`

## 范围

只修改 frozen-carton-app 中与以下链路直接相关的文件：

- 严格排柜核心与适配器；
- 产品池重排外挂模块；
- 浏览器端 Excel 导出；
- bootstrap 装载入口；
- 定向测试与 package scripts；
- 必要的 GitHub Actions 校验入口。

不修改：

- 原产品生命周期业务顺序；
- 店员端正式数据流程；
- 原有页面主体布局和业务模块；
- 无关 CSS/JS；
- 其他仓库或历史副本。

## 唯一排柜引擎

沿用已验收的 deterministic strict allocation core，禁止新建第二套算法。

输入统一为：

- 最新有效产品池；
- 门店冰柜配置；
- 当前正式陈列位置作为老品位置偏好（可选）；
- 10%触发参数；
- 754L 外储上限；
- 当前 P95 系数。

输出统一为：

- 门店排柜草稿；
- SKU 纳入/未纳入结果；
- 陈列柜、具体位置、列数、单列容量、单列占宽；
- 满陈、触发库存、直接整箱、需外储、外储体积、周转；
- 柜段余量；
- 严格校验结果。

## 最新有效产品池

产品池只保留生命周期有效商品：

- 在售SKU；
- 上新完成。

淘汰完成/已淘汰商品不参与排柜。SKU 数量动态读取，不写死 67、71 或其他数量。

## 老品增量保位

产品池变化时优先做增量重排：

1. 最新产品池中仍有效的老 SKU，优先保留原柜型/原柜段位置；
2. 淘汰 SKU 释放空间；
3. 新品进入释放空间和同四级/同三级/同场景相邻空间；
4. 只有在覆盖、外储、品类集中或物理校验不通过时才由严格引擎局部重新选择位置；
5. 原位置只作为“偏好”，不得突破物理、冰品隔离、同 SKU 集中、754L 等硬规则。

新增门店没有历史位置，直接使用同一严格引擎全量排柜。

## 当前锁定物理规则

- 水平面允许长宽旋转 90°；高度不翻转；
- 卧柜/冰淇淋柜按真实深度和有效高度允许堆叠；
- 立柜第1–5层为冻品销售层，不垂直堆叠；
- 立柜第6层固定存储位；
- **柜4第1–5层全部正常参与冻品排柜，不再存在柜4 1–4层预留规则**；
- 冰品只进入冰淇淋柜，普通冻品不得进入冰淇淋柜；
- 同一 SKU 同一柜型只允许一个位置；
- A/B 级可同时使用立柜+卧柜；C/D 原则上单柜型单位置；
- 四级品类和同类型商品优先连续/相邻；
- 柜段不得超宽；
- 建议外储必须 <= 754L；
- 优先保留 SKU 覆盖，再优化整箱到店和外储；
- 未排入商品不得从产品池自动删除，必须保留中文原因。

## 产品池重排外挂模块

不改 app.js 主体业务，新增独立模块并在现有“导入导出”运营页中插入“产品池重排”面板。

四个按钮：

1. **导出当前产品池**
   - 读取 ProductLifecycle 当前有效产品；
   - 下载 `产品池_当前版.xlsx`。

2. **按当前产品池重新排柜**
   - 对全部现有门店运行统一严格引擎；
   - 新增门店若已存在于小程序门店/柜段数据，同样自动处理；
   - 将结果写入独立运营草稿 localStorage，不覆盖发布状态；
   - 草稿包含未排入商品及原因；
   - 显示门店通过/需复核/失败数量与中文原因。

3. **人工复核**
   - 载入生成的草稿并进入现有运营模式；
   - 复用当前“排柜调整”和“陈列图”手工编辑能力；
   - 现有 app.js 已对列数、单列容量、单列占宽等修改联动满陈、柜段余量和外储；
   - 未人工确认前不触碰发布状态。

4. **导出最新版底表**
   - 从当前运营草稿导出 `整箱到店数据测算_当前版.xlsx`；
   - Sheet 结构与 GitHub 自动转换链路兼容；
   - 包含最新产品池、SKU明细、外储、柜段余量、未排入清单、规则说明等。

## Excel 输出

浏览器端不依赖外部 CDN，使用轻量 OOXML writer 生成真正的 `.xlsx`。

正式底表至少保持现有 GitHub `source-to-app-data.mjs` 所消费的 Sheet：

- `10%触发_门店汇总`
- `10%触发_SKU明细`
- `10%触发_外储明细`
- `10%触发_柜段余量`
- `10%触发_未排入SKU清单`
- `71SKU有效池明细`（历史兼容名称，内容为动态有效池）
- `测算规则说明`

并补齐当前复用规则需要的：

- `三级类目集中复核`
- `复核说明`

## GitHub 发布

继续使用现有 `data/source/*.xlsx → npm run refresh-data → verify → app-data.json` 自动流程。

规则：

- Actions 复核失败时命令退出，不提交新 app-data，因此保留上一版正式小程序数据；
- 失败原因在 Actions 日志/summary 中显示中文错误；
- 用户只需要把导出的同名 Excel 上传到 `data/source/`，不需要手改 app-data.json。

## 验收

必须通过：

1. 最新有效产品池动态读取；
2. 柜4第1–5层可用，第6层存储；
3. 冰品隔离；
4. 同 SKU 同柜型不拆分；
5. 柜段不超宽；
6. 10%触发计算正确；
7. 建议外储 <=754L 或明确失败；
8. 未排入 SKU 有中文原因且仍在草稿/底表；
9. 老品合法原位置可优先保留；
10. 新增门店无历史位置也可用同一引擎生成；
11. 草稿不会覆盖发布状态；
12. 两种 Excel 均为真实 xlsx，可被 openpyxl/SheetJS 读取；
13. 导出正式底表能被现有 `source-to-app-data.mjs` 消费；
14. 所有用户可见提示均为中文。
